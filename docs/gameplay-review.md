| onset | 登録音との判定 | score | margin | 判定 |

## 2026-09-15 ラウンド開始から両提示までの修正

SHA-256 d6498c4d52531b0818c50231915867e6dc11ce57b6e16963534647f2753ccfca です。

登録済み7音との一致から、PASS1を7.80 / 9.10 / 10.40秒、
PASS2を14.70 / 15.98 / 17.30秒に分離しました。両方とも中央 → 右1 → 右2です。

| 提示 | 中央 | 右1 | 右2 |
|---|---:|---:|---:|
| PASS1 score | 0.929 | 0.934 | 0.950 |

直近1秒の低い側のRMSから環境音量を推定し、固定しきい値を上限として開始値を自動調整します。

## 収集

Replayの保存チェック、または「記録」タブで収集を選びます。

- 認識ログを保存：判定、全7候補、理由、元音声情報をJSONLに記録します。
- 不確かな音声を保存：LOW / REJECTEDの候補、duplicate、両PASSが確定できない問題箇所の短い元音声を保存します。
- 採用音声も保存：HIGH / MEDIUMで採用した音も収集します。初期OFFです。正解かは手動で確認します。

音声とJSONL保存は独立しています。ログから音声を開くには収集時に認識ログもONにします。
全セッション録音は初期OFFで、この段階の自動収集は短いイベント音声です。
通しWAVがあればReplayで区間ごとに確認できます。

不一致等では採用した音も証拠として保存します。元のHIGH等の判定は変えず、問題理由を別に記録します。
最大14音 / 32 MiBを保持し、各音の追加保存は1回までです。1保存窓は3秒 / 16 MiB以内です。
保存失敗は解析結果を維持して案内します。

## 手動の正解付け

1. Liveの「音声の保存・Replayを開く」を展開し、「Incorrect（直近の音）」を押します。
2. Replayの固定コピーで元の判定・候補と音声を確認します。正解欄は空のままです。
3. 「誤認識・確認用の音声を保存」で保存区間、正解、分類、由来、メモを入力します。
4. 選択音はOracle 1種類、Oracleなしなら「なし」です。連続イベント・両PASSは「音声全体」と対応する単位を選びます。
5. 「正解を付けて保存」を押します。

「記録」でログフォルダーを選び、音声のある行からReplayへ開くこともできます。
フォルダー外への参照を拒否し、元音声checksumがあれば一致を検証します。
古いログでchecksumがない場合は同一性の検証情報がありません。
読めない行の案内を残し、最大200ファイル / 64 MiB、最新2000行まで表示します。

```text
%LOCALAPPDATA%\OracleAssistant\review\cases\<id>\
  audio.wav      元形式の確認区間
  manifest.json  手動の正解・分類・由来
  analysis.json  元判定・候補・条件・checksum
```

元音声・元判定を保持し、手動の正解を別に保存します。
Liveの直近音は現在の認識世代に限定し、Stop / Reset / 入力変更で古い音を選べなくします。

## 改善の手順

「記録」の「手動記録を一括評価」で固定Datasetを作り、「評価」タブで実行します。
指標と比較は[Dataset評価](dataset-evaluation.md)を参照してください。

1. 変更前のレポートを保存します。
2. Replayで時刻、元音声、候補差、各成分スコア、切り出し理由を確認します。
3. 問題に対応した設定を1つずつ変更した候補JSON、または別テンプレートバンクを用意します。
4. 同じWAV・正解をCLI評価し、比較元report.jsonと数値を比較します。
5. Oracle別の正解率と誤検出・棄却の増減を確認します。採用率の上昇だけでは改善と扱いません。

根拠のないアルゴリズム・閾値変更は行いません。
提供7音の自己一致と人工条件は収集・再現・比較機能の検証です。
実戦の残響、会話、効果音、独立録音を含む改善確認は[受け入れ記録](acceptance.md)の未完了項目です。
